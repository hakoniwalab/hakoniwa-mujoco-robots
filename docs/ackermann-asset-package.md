# Generic Ackermann Asset Package

One compiled Hakoniwa asset runs different four-wheel Ackermann MJCF models.
Vehicle-specific C++ implementations are not part of the contract.

## MuJoCo model formats

The shared world loader accepts canonical MuJoCo XML (`.xml`) and compiled
MuJoCo binary models (`.mjb`). XML remains the editable, portable source of
truth. MJB is a generated runtime artifact for large composed worlds where XML
compilation would otherwise delay every startup.

MJB files are bound to the MuJoCo version used to generate them. Generate and
reload-validate an MJB with the same MuJoCo shared library used by the consuming
asset, record the source XML, MJB, and library hashes, and regenerate the MJB
after a MuJoCo upgrade. Hakoniwa Business Pack provides
`tools/mujoco_model_compiler.py` for this materialization contract.

## Package contract

```text
asset-manifest.json
  ├── model             generated MuJoCo world
  ├── pdu_def           shared game-controller PDU
  ├── endpoint          shared endpoint configuration
  ├── components        four actuator component configs
  └── runtime_config    Ackermann-specific semantic contract
```

`ackermann-runtime.json` contains:

- geometry: wheelbase, track, wheel radius, steering and wheel limits
- bindings: semantic roles mapped to component, joint, and actuator names
- control: manual speed, deadzone, slew rates, and real-time pacing
- smoke: model-independent C++ dynamic smoke-test inputs and limits

Its schema is
`config/assets/schema/ackermann-runtime.schema.json`. The general Asset
Manifest schema only gains the optional `runtime_config` path, so existing
non-Ackermann packages retain their current contract.

## Validation layers

```bash
FOUNDATION=../hakoniwa-business-pack/work/foundation/install/python/bin/python3

$FOUNDATION tools/validate_ackermann_asset_package.py \
  recipes/generic_ackermann/asset-manifest.json \
  recipes/hunter/asset-manifest.json

python3.12 tools/recipe/generic_ackermann.py smoke --vehicle golf-cart
python3.12 tools/recipe/generic_ackermann.py smoke --vehicle hunter
```

The package validator checks both JSON Schemas, referenced files, semantic
component IDs, component-to-joint/actuator consistency, and names in the loaded
MJCF. The shared C++ binary then verifies idle, straight, and turn behavior.
The deeper MBody validator independently runs left/right scenarios, scoring,
RTF, numerical stability, and Forge reproducibility.

## Adding another vehicle

1. Add the reproducible body and headless validation Recipe to
   `hakoniwa-mbody-registry`.
2. Add four joint actuator component JSON files if its semantic names differ.
3. Add `recipes/<vehicle>/asset-manifest.json`.
4. Add schema-valid `recipes/<vehicle>/ackermann-runtime.json`.
5. Add a profile to `tools/recipe/generic_ackermann.py`.
6. Run package diagnostics, the shared binary smoke test, and MBody validation.
7. Only then add the Launcher/PS5 Recipe.

The model generated by Forge is never hand-edited. Optuna candidates also
remain evidence until a person promotes accepted values into MBody YAML and
reruns the complete chain.
